# 0004. Idempotency keys for order placement

- **Status:** Accepted
- **Date:** 2026-10-01

## Context

Mobile networks drop connections. A client that does not receive the response to "place order" cannot know whether
the order was created. If it retries, the customer may get two orders (and two charges); if it does not, the
customer may think the order failed.

## Decision

`POST /api/v1/orders` requires an `Idempotency-Key` header, generated by the client once per order attempt (a UUID)
and reused for retries. `IdempotencyService`:

- stores the key, a SHA-256 hash of the request body and the response, in the same transaction as the order;
- inserts the key **before** running the use case, so a concurrent duplicate blocks on the unique index and then
  receives `409 IDEMPOTENCY_KEY_IN_FLIGHT`;
- replays the stored response for a retry with the same body (`Idempotent-Replayed: true`);
- rejects the same key with a different body (`422 IDEMPOTENCY_KEY_REUSED`), which is a client bug;
- scopes keys to the authenticated customer.

Failed requests are not stored: the transaction rolls back, so the client can retry with the same key.

## Consequences

- Retries are always safe for clients. This is the pattern used by payment APIs such as Stripe.
- Clients must generate and keep a key per attempt.
- The `idempotency_keys` table needs a retention policy (backlog KST-107).
- New endpoints with side effects that clients may retry (refunds...) should use the same service.
